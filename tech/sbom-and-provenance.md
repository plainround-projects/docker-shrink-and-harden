# SBOM (SPDX) and build provenance (SLSA)

## What it is

An **SBOM**, a software bill of materials, is a list of everything inside a piece of software: every package, with its version. Think of the ingredient list on food. This repository's SBOM is in **SPDX** format, a standard JSON layout for such lists.

**Provenance** is a record of how and where an artifact was built: which source, which build steps, which base images (by digest), which arguments. It follows the **SLSA** ("Supply-chain Levels for Software Artifacts") format. Together they let you answer "what is in this image, and where did it come from?" without opening it.

## Why this repository uses it

Step 6 of the lesson: "answer 'does this image contain library X, and which version?' from the SBOM alone". When a new vulnerability is announced you can check every image you ship by reading its SBOM instead of unpacking it.

## How it works underneath

BuildKit runs a scanner (Syft, in the `docker/buildkit-syft-scanner` image) over the finished image. It finds packages from the Debian database files and from the metadata Go embeds in every binary (the Go version and module list). It writes an SPDX document and stores it in the registry as a separate manifest beside the image, tied to it by digest. Provenance is generated by BuildKit itself from the build's inputs. Neither changes the image's layers.

In the SPDX JSON, `packages` is a list of objects with `name` and `versionInfo`. For a Go binary, `stdlib` is the Go standard library and its `versionInfo` is the Go version that compiled the program (`go1.26.10`). In the provenance (SLSA v1 layout), `buildDefinition.buildType` names the build system, and `buildDefinition.resolvedDependencies` lists inputs with their digests.

## Walkthrough of this repository's use

```bash
#!/usr/bin/env bash
# Build v4: the same Dockerfile as v3, built with an SBOM and provenance attestation and pushed to the local registry.
# Then answer "which packages are inside, and was it built from this commit?" from the registry alone.
set -euo pipefail
# shellcheck source=lib.sh
. "$(dirname "$0")/lib.sh"
cd "${ROOT}"

say "Build and push svc:v4 with --sbom=true --provenance=mode=max (needs the docker-container builder)"
docker buildx build --builder "${BUILDER}" --sbom=true --provenance=mode=max --push \
  --secret "id=netrc,src=${ROOT}/netrc" --build-arg VERSION=v4 --build-arg "COMMIT=$(git rev-parse --short=12 HEAD 2>/dev/null || echo unknown)" --tag "${REGISTRY}/svc:v4" .

say "Packages in the SBOM"
docker buildx imagetools inspect "${REGISTRY}/svc:v4" --format '{{ json .SBOM }}' | jq -r '.SPDX.packages[] | select(.versionInfo != null) | "\(.name) \(.versionInfo)"' | sort

say "Does the image contain the Go standard library, and which version?"
docker buildx imagetools inspect "${REGISTRY}/svc:v4" --format '{{ json .SBOM }}' | jq -r '.SPDX.packages[] | select(.name == "stdlib") | "\(.name) \(.versionInfo)"'

say "Provenance: what built this image, and from which pinned inputs"
provenance="$(docker buildx imagetools inspect "${REGISTRY}/svc:v4" --format '{{ json .Provenance }}')"
echo "${provenance}" | jq -r '"build type: \(.SLSA.buildDefinition.buildType)"'
echo "${provenance}" | jq -r '.SLSA.buildDefinition.resolvedDependencies[]? | "input: \(.uri) \(.digest | to_entries[0] | "\(.key):\(.value[0:19])...")"'
```

- `--format '{{ json .SBOM }}'` is a Go template that prints the SBOM attestation as JSON.
- `jq -r '.SPDX.packages[] | select(.versionInfo != null) | "\(.name) \(.versionInfo)"' | sort` loops over the packages (`[]`), keeps those with a version, builds the text `name version` with string interpolation `\( ... )`, and sorts. Result for v4: Debian's `base-files`, `ca-certificates`, `media-types`, `netbase`, `tzdata` (the distroless contents), `example.com/svc` and `stdlib go1.26.10`.
- The provenance block prints the build type URL and one line per resolved input: the builder scanner image, the `golang:1.26-bookworm` base and the distroless base, each with its digest. These are exactly the digests pinned in the Dockerfile.

The answer to the lesson's question: `docker buildx imagetools inspect localhost:5057/svc:v4 --format '{{ json .SBOM }}' | jq -r '.SPDX.packages[].name' | grep -i stdlib` prints `stdlib`.

## Try it yourself

1. Build and read: `make sbom`. Expected: the package list ends with `stdlib go1.26.10`.
2. Ask a yes/no question of the SBOM: `docker buildx imagetools inspect localhost:5057/svc:v4 --format '{{ json .SBOM }}' | jq '[.SPDX.packages[] | select(.name=="stdlib")] | length'`. Expected: `1`.
3. List the digests the build used: `docker buildx imagetools inspect localhost:5057/svc:v4 --format '{{ json .Provenance }}' | jq -r '.SLSA.buildDefinition.resolvedDependencies[].uri'`. Expected: three `pkg:docker/...` lines.
4. Run the test: `tests/e2e/06_sbom_and_provenance.sh`. Expected: five `PASS` lines and `OK`.

## Mistakes people make

- Believing an SBOM proves the software is safe. It lists contents; you still need a scanner.
- Generating one at build time and losing it. Here it lives in the registry next to the image.
- Treating `UNKNOWN` version of `example.com/svc` as an error: a local module has no released version.

## Check yourself

1. What is an SBOM? *A list of all packages and versions inside an image.*
2. What is `stdlib` in the SBOM? *The Go standard library, with the Go version that built the binary.*
3. What does provenance add? *How, where and from which inputs the image was built.*
4. Where are the documents stored? *In the registry, as manifests beside the image.*
5. Why does the build need `--push`? *Attestations are stored in the registry; they cannot be loaded into the local engine.*
